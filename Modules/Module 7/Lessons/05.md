# Introduction

So far, you've learned:

```text id="sp001"
SELECT

JOINS

GROUP BY

Subqueries

Views
```

These tools help retrieve and organize data.

However, in enterprise systems, business logic often needs to be:

```text id="sp002"
Reusable

Secure

Automated

Centralized
```

Instead of rewriting SQL repeatedly, developers create:

```text id="sp003"
Stored Procedures
```

---

# What is a Stored Procedure?

A Stored Procedure is a saved SQL program stored inside a database.

It contains:

```text id="sp004"
SQL Statements

Business Logic

Parameters

Control Flow
```

that can be executed whenever needed.

---

# Visual Representation

```text id="sp005"
Application
      ↓
Stored Procedure
      ↓
Database
      ↓
Results
```

---

# Real-World Example

Without a Stored Procedure:

```sql id="sp006"
SELECT
    BookID,
    Title,
    BookPrice
FROM Books;
```

Every developer must write the query repeatedly.

---

With a Stored Procedure:

```sql id="sp007"
EXEC GetAllBooks;
```

The logic is written once and reused many times.

---

# Why Use Stored Procedures?

Stored Procedures provide:

### Reusability

Write once.

Execute many times.

---

### Security

Control database access.

---

### Performance

Precompiled execution plans.

---

### Centralized Logic

Business rules stay in one place.

---

### Automation

Support dashboards and applications.

---

# Stored Procedures vs Views

| Feature                | View    | Stored Procedure |
| ---------------------- | ------- | ---------------- |
| Stores Query           | Yes     | Yes              |
| Accepts Parameters     | No      | Yes              |
| Returns Result Sets    | Yes     | Yes              |
| Contains Logic         | Limited | Yes              |
| Supports INSERT/UPDATE | Limited | Yes              |
| Used For Automation    | No      | Yes              |

# Advantages of Stored Procedures

---

## Reusability

One Procedure:

```sql id="sp028"
GetAllBooks
```

can be used by:

```text id="sp029"
Web Apps

Mobile Apps

Reports

Dashboards
```

---

## Security

Grant access to Procedure.

Restrict access to tables.

---

Example:

```text id="sp030"
Users Run Procedure

Users Cannot Query Tables Directly
```

---

## Performance

SQL Server stores execution plans.

Benefits:

```text id="sp031"
Faster Repeated Execution
```

---

## Maintainability

Change logic once.

All applications receive updates.

---

# Example: Reporting Procedure

```sql id="sp032"
CREATE PROCEDURE GetBookCatalog
AS
BEGIN

    SELECT
        B.Title,
        C.CategoryName,
        P.PublisherName,
        B.BookPrice
    FROM Books B
    INNER JOIN Categories C
        ON B.CategoryID = C.CategoryID
    INNER JOIN Publishers P
        ON B.PublisherID = P.PublisherID;

END;
```

---

Execute:

```sql id="sp033"
EXEC GetBookCatalog;
```

---

# Common Beginner Mistakes

---

## Forgetting BEGIN END

Bad:

```sql id="sp040"
CREATE PROCEDURE GetBooks
AS

SELECT *
FROM Books;
```

---

Better:

```sql id="sp041"
CREATE PROCEDURE GetBooks
AS
BEGIN

    SELECT *
    FROM Books;

END;
```

---

## Poor Naming

Bad:

```text id="sp042"
Proc1
```

---

Better:

```text id="sp043"
GetAllBooks
```

---

## Creating Procedures for Simple One-Time Queries

Use procedures only when logic is reusable.

---

## Confusing Views and Procedures

Remember:

```text id="sp044"
Views = Virtual Tables

Stored Procedures = Saved Programs
```
